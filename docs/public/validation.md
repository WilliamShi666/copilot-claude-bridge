# Validation scope

The initial release preparation is based on local native Claude Code 2.1.296 sessions with Windows Chrome and a signed-in Excel web Copilot account. The source includes self-contained automated tests; private account sessions, screenshots, workbook identifiers and transcripts are deliberately excluded.

## Automated checks

The agent-isolation repair contains 129 Node tests covering protocol/tool validation, loopback authentication, pairing, cancellation, duplicate handling, reply reception, context continuity, auxiliary lanes, ordered packet transfer, startup readiness, summary semantics, independent agent contexts and reset/dispatch cancellation races. Two source-export checks run separately. Clean source installation, typechecking, builds and all 131 checks passed locally on Ubuntu WSL / Node 22 and Windows / Node 24 during release preparation. A ledger assertion reads after shutdown/flush to avoid Windows reader-versus-rename locking. CI is configured for Node 22/24 on Ubuntu and Windows; its hosted runs must be checked after publication.

The startup/switching repair adds launcher and saved-gateway coverage: 134 runtime tests, six launcher checks and two source-export checks. The updated suite passed on Windows Node 24 and Ubuntu WSL Node 22. Separate live process checks on both OSes passed cold start, reuse, restart after an explicit gateway stop and preservation of the client credential. These checks simulate a gateway process restart, not a full Windows reboot.

## Native agents and in-process teams

Claude Code 2.1.296 was exercised interactively on Ubuntu WSL through the signed-in Windows Chrome workbook. Three unnamed subagents were launched in one assistant response and returned their three distinct markers. Three named in-process teammates were also launched together; each used native Write and Read for a different file. The same teammates then received three SendMessage follow-ups, recalled their own original markers, and wrote/read three further files. Child transcripts, independently read file contents and gateway identities confirmed separate agent lanes, continuation at epoch 1 and no overlapping-context 409 errors. Each write was approved individually in session-only standard permission mode. Saved provider settings were retained.

Stopping one named teammate from the native panel did not stop the other two, which completed afterward. In this client build, the stopped teammate did not immediately close its pending HTTP request; that request still ran through the browser queue. Gateway tests separately verify that an actual client disconnect before submission rolls back only the affected agent, never sends a late job, and leaves sibling work running. Do not equate the native panel's stop indication with immediate upstream inference cancellation.

After the readiness and unsent-editor repairs, a fresh native Auto-mode session launched three named teammates in one assistant response. All three passed the native permission classifier and returned their separate markers without retries. The same three teammates then received three SendMessage follow-ups in one response; each recalled its original complete sentence and marker, used native Write and Read for its own file, and ran native Bash `pwd`. Independent file reads matched the actual Write arguments byte for byte; native tool results succeeded, each agent continued its original lane at epoch 1, and no gateway failures or native API errors occurred. No manual Yes approvals or saved permission-setting changes were used. This is limited acceptance of the tested in-process scenario, not certification of arbitrary Auto-mode tasks or split-pane teams.

## Same-chat cancellation continuation

The cancellation-continuation update passes 263 runtime tests, six launcher checks and two source-export checks on Windows Node 24 and Ubuntu WSL Node 22. Coverage includes no/partial/complete browser answers, unfinished JSON, cancellation before content dispatch, durable and duplicate receipts, reconnect, wrong nonce/page identity, merged tool results, trailing environment messages, sibling isolation, draft preservation, partial bootstrap transfer, late provider refusals and full-recovery size failures. Same-chat/epoch continuity, measured delta size and side-effect counts still require separate live acceptance; these automated results do not establish provider cache hits.

Native Ubuntu WSL Claude Code 2.1.300 completed three consecutive real mid-request Escape/feedback cycles in Auto Mode. Each interruption followed an actual one-time Bash log append. All recovery requests and subsequent Write/Read tool rounds used one Copilot chat at epoch 1 with zero rebuilds and no native API errors. Recovery deltas were 2,736, 1,960 and 1,952 characters; cancellation confirmation took about 9.3–9.7 seconds and the first recovery responses about 9.6–13.6 seconds. Independent disk checks found exactly three log lines and the requested final file contents. A separate post-completion feedback turn wrote/read the final marker without repeating the side effect. Bridge-driven image live acceptance remains a separate release gate.

Native Windows Claude Code 2.1.296 also completed three consecutive real Escape/feedback cycles in Auto Mode, followed by a separate post-completion feedback. All main requests before the separate rebuild test used one Copilot chat at epoch 1, with no failures or rebuilds. Resume deltas were 1,966, 2,136 and 1,952 characters; cancellation confirmation took about 5.9–10.0 seconds and the first resume responses about 8.1–9.8 seconds. Native transcripts contained exactly three Bash append commands and independent disk reads found exactly the three requested log lines. Rounds one and three were interrupted before the pending Write returned; round two was interrupted later, after Write completed and before its follow-up Read returned. Each resumed Write/Read and the final feedback produced the requested disk contents without repeating Bash.

A separate Windows recovery test switched the original Copilot chat and left an unsent test draft. The next native feedback triggered exactly one isolated full bootstrap (200,945 characters) in a new workbook tab at epoch 2. The native transcript displayed the bridge full-sync notice, subsequent Write/Read completed and the three-line side-effect log was unchanged. Native browser inspection of the original tab confirmed its unsent draft remained intact. This recovery test is separate from the three same-chat cycles; the full bootstrap is not counted as an incremental continuation.

## Native image live acceptance

The opt-in image build uses a restricted Chrome debugger input driver and a default-off runtime switch. Automated checks cover image byte validation, attachment identity/delivery, current-composer preview and upload readiness, delayed inline File references, job/frame/model/nonce/draft/focus rejection, cancellation cleanup, no repeated input and ordered summary fallback. Default text and explicit image build manifests were verified separately.

Live diagnosis found that decoded upload previews can precede both the decorative upload spinner's completion and the editor's inline File reference. The bridge now waits for all three before freezing the exact draft, and retains scoped focus/input ownership until the independently verified submitted message arrives. The final small automatic request completed in about 16.4 seconds with the correct unseen marker and shapes, without manual submission. Earlier manual and failed automatic attempts are diagnostic evidence only.

The first native Windows image flow automatically Read the image, identified its unseen marker/shapes and Write the correct report, but the subsequent report-Read request failed because Copilot emitted prose outside the required JSON. The strict parser rejected that response without inventing or executing a tool call. This failed run is retained and is not counted as full native acceptance. A fresh Windows Claude Code 2.1.296 Auto Mode session then completed automatic PNG and JPEG Read → vision → Write → Read, followed by Edit/Read feedback without another image read. Both unseen markers and the three shapes matched independently stored fixtures and disk contents; native tools contained no OCR, Bash or MCP calls. The initial format failure remains a separate failed run. Ubuntu WSL Claude Code 2.1.300 subsequently passed the same automatic PNG/JPEG and post-image Edit/Read sequence. Each OS retained one Copilot chat at epoch 1 throughout its successful image session. Each new image was uploaded once; subsequent tool-result and feedback rounds uploaded no old images. The two successful sessions each used only native Read/Write/Edit. Independent disk checks matched both fixture markers, all three shapes and final feedback markers. No manual browser submit, OCR or external vision fallback was used in these accepted runs.

## Earlier interruption and follow-up feedback

The feedback repair passes 139 runtime checks, including dispatched cancellation, identical retry rejection, merged tool-result feedback, trailing native system messages, and recovery attempts that fail before submission. Launcher/export checks remain separate. These checks passed with Windows Node 24 and Ubuntu WSL Node 22.

In native Ubuntu WSL Claude Code 2.1.300 Auto Mode, an AskUserQuestion answer started a main request. Its actual dispatch was observed before sending native Escape to interrupt it. The ledger recorded exactly one canceled job. Explicit new user feedback then completed a full `client-interrupted-feedback` bootstrap in a new Copilot chat, followed by native Write/Read with independently verified file contents. After that task finished, another feedback turn changed and read the file again using ordinary delta continuation. The final repaired sequence had no native uncertain-context API errors. The earlier live run exposed trailing system environment messages and failed before that handling was added; it is not counted as a successful recovery.

The client's current history remains authoritative. The bridge does not automatically resend the abandoned job or execute tools itself. Rewritten history, tool-only changes and unknown delivery retain explicit recovery requirements described in [context.md](context.md).

The closed-main startup repair passes 268 runtime tests, six launcher checks and two source-export checks on Windows Node 24 and Ubuntu WSL Node 22. ## Lifetime registry retention

The lifetime-cap removal passes 274 runtime tests plus six launcher and two export checks on Windows Node 24 and Ubuntu WSL Node 22. Regression cases reproduce all three former 100-record errors before the fix. They create 150 entries, load and extend 1,200-entry registries, preserve terminal refusal/running-compaction state, and execute 105 simulated browser generations followed by restart and same-chat delta continuation. No history is evicted or reset.

The live WSL account registry started with exactly 100 conversation handles. After updating the idle gateways, all original handles and native contexts were retained. Real WSL Claude Code 2.1.300 and Windows Claude Code 2.1.296 Auto Mode clients completed Write/Read through the already connected WSL gateway, using explicitly isolated test-agent headers so the user's main conversation was not changed. The registry reached 103 and then 104 handles. A WSL preparation attempt timed out before submission; it remains recorded as a failed setup. The accepted WSL turn followed refreshing/opening that isolated Copilot pane, without manually submitting its request. The accepted Windows turn completed without that setup intervention.

With 103 handles present, the WSL gateway was stopped only while idle and restarted. Every handle loaded again, the same native test conversation continued with a delta at epoch 1, and an additional native Read confirmed the existing disk marker without another Write. The original user main chat remained ready with the same cursor throughout. These checks establish removal of the count ceiling and the tested restart behavior, not a multi-day soak or an upstream capacity guarantee.
