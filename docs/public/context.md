# Native context, browser chats and compaction

Claude Code remains the source of the conversation. Its request contains the system instructions, available tool schemas, messages and tool results. The bridge serializes text and stable image references into Copilot chat prompts, sends base64 image pixels separately through real browser attachments, and validates the structured response before returning native text/tool events.

Resumed/forked histories can contain assistant `thinking` or `redacted_thinking` blocks from another provider. The request parser validates their shape, excludes the complete blocks from its transport copy and omits resulting reasoning-only assistant messages. Native transcripts, ordinary text, tool IDs/results, schemas and images are not edited. Signatures are never interpreted, forged or converted to visible text. Token estimates and context fingerprints use the same projected history, so reasoning-only changes do not force a new bootstrap. Reasoning in user/system/tool-result content, malformed blocks and unknown content types still fail explicitly.

The main lane bootstraps full context once, then sends appended messages and changed request fields to the verified active Copilot chat. A changed tool list can still produce a large update. The bridge compares the current browser conversation fingerprint before continuing. It does not restore arbitrary old Office chats from the history sidebar. Keep one active main client session per paired workbook.

Subagents and in-process teammates use native `x-claude-code-agent-id` together with session ID and model. Their independent leases, snapshots, browser lanes and owned tabs preserve continuation when another agent takes its turn. Agent compaction hints and hook events are scoped to the requesting agent. Model requests queue globally; queued requests have a bounded wait budget separate from their generation timeout. A canceled queued request is never sent to the browser. Overlapping main requests for the same session/agent/model still fail rather than mixing histories.

Title requests and native compaction run in bridge-owned auxiliary browser tabs/chats. They do not append to the main conversation. Seeing these additional sessions in Copilot is expected. A long source is transmitted in ordered packets, each acknowledged before the next is sent. The final packet asks for the actual response; intermediate acknowledgments are not native model answers. The UI packet cap is 350,000 characters; serialized escaping reduces each packet's available source capacity. Source text is not silently truncated.

A completed ACK reply that is a truncated prefix of the exact expected JSON can receive up to five short corrections per complete transfer. Before every correction the bridge verifies source-message ownership, unchanged page/history and an empty draft, then requests only that ACK in the same chat/model. It never resends source packets or forwards intermediate tools. Wrong IDs, incorrect envelopes, prose, cancellation, refusal and changed pages/drafts stop immediately; exhausted corrections report their phase, count and cause. Source-free diagnostics contain `contextAckRepairs` and `contextAckRepairChars`; summary routing can aggregate five corrections from each of its two model attempts. Successful non-streamed responses may carry matching `x-bridge-context-ack-*` headers.

## Image inputs

Image input requires the explicit `npm run build:images` extension build and a separate default-off **Enable image input** switch in the popup. The image build adds Chrome's required `debugger` permission; the default text build does not. Chrome does not permit `debugger` as an optional runtime grant. The extension verifies job/lane/tab/frame, originating document, a nonce, allowed model attempt, unchanged prompt/images and the same observed editor and native Send button before and after attaching. It temporarily emulates focused-page state in that target tab, requires both native Send-button focus and document focus, sends one Enter, verifies trusted delivery to that button, releases Enter immediately, then waits read-only for the exact owned user message before restoring page-focus emulation and detaching. Every current inline File reference must be present in the exact unique attachment filename set before the unchanged draft is frozen. The current draft thumbnail must be fully loaded, and actual attachment-upload indicators block input even if the preview and Send button are already visible. The decorative upload spinner need not expose a progressbar role. After input, draft mutations are preserved while the bridge waits read-only for the owned message. Cancellation or bounded acknowledgement failure releases the connection without another submit. This permission is inherently broader than this build's narrow commands; see [SECURITY.md](../../SECURITY.md). It never detaches another debugger. Unknown delivery is not retried. A permitted summary-model fallback has its own ordered submission identity, rather than resending a prior attempt. Switching the feature off or disconnecting stops its use; removing the required permission needs a default text rebuild/reload or uninstall. Matching content capability, image build permission and enabled switch are required before the gateway leases an image request.

Native Read results may contain image blocks nested inside `tool_result`. These are validated as base64 PNG/JPEG/GIF/WebP, fingerprinted, and replaced in the textual request by a deterministic attachment filename. Only images required by the current bootstrap/delta/replacement tail are uploaded; unchanged old images are not resent during ordinary feedback. The sent browser message must contain independently verified loaded attachment thumbnails for every expected filename (plain prompt text is not accepted as evidence), and its authenticated result must return matching image IDs before a native answer is delivered.

The image build requires Chrome 125+ for flattened child debugger sessions. Focus emulation covers the verified tab and its related Excel/Copilot iframe targets; top-level focus alone is insufficient for an out-of-process Copilot frame. The driver recursively attaches only to exact HTTPS Office iframe origins below that tab, rejects unrelated targets and restores all scoped overrides on release. It does not focus the browser window or enable Runtime/Network/cookie inspection. See [Chrome's frame/session documentation](https://developer.chrome.com/docs/extensions/reference/api/debugger#attach-to-related-targets).

The write-ahead journal is separate from actual input delivery. A completed driver failure before invoking Enter reports `inputAttempted: false`; with no earlier source packets sent, the failure reports `submitted: false` and preserves the committed native context. Owned unsent drafts remain intact, so a retry may require explicit draft handling or the existing single isolated recovery. Once Enter may have been invoked, or earlier context packets were sent, delivery remains uncertain. Image-input failures also stop summary-model fallback without replacing this evidence with a generic draft error. Missing/legacy evidence never becomes proof that an old request was unsent.

This prevents a valid image in native history from permanently blocking every following request with an unsupported-content 400. Existing sessions that failed only during image validation can continue after updating matching gateway and extension builds; they retain their image source and native tool history. Unknown delivery and genuine upstream refusals retain their separate recovery rules below.

The transport limits are 5 MB per image, 10 MB of unique image data in one native request and five attachments in a browser turn. It never silently truncates or substitutes a textual visual guess. Remote image URLs are not fetched. Image-related token estimates use a fixed local allowance rather than counting base64 as text; they are not measured visual token usage.

Image interpretation uses Copilot's built-in attachment/vision capability. The reference is not a text-only native Read result. Restricting all visual analysis can also prevent that built-in viewing; no local OCR or external vision tool is automatically invoked. A verified thumbnail proves the attachment was delivered, not that a model interpreted it correctly or that a particular internal vision model processed it. Check the actual answer against a known image.

## Thresholds

The launcher applies native model overrides and `CLAUDE_CODE_AUTO_COMPACT_WINDOW` in a temporary session settings file. Its default is `533000`, with the older percentage override cleared. The tested Claude Code build reserves enough room that this targets roughly 500k input tokens. Change the native threshold with `--compact-window 200k` or another supported integer from 100k to 1m. Reserves and recognition behavior can change with client versions.

The gateway's independent prompt cap is measured in **characters**, not tokens. The default is 180,000 characters. Long-context operation requires starting it with `--max-prompt-chars 2000000` (the maximum). A larger client window alone does not increase this transport cap. Token counters are local heuristics, especially approximate for mixed-language text and tool schemas.

## Compaction

1. Native Claude Code requests manual `/compact` or automatic compaction.
2. The bridge sends the complete summary request to a fresh auxiliary chat, using GPT-6.1 Sol.
3. Recoverable UI/JSON-format errors can start a fresh GPT-6 Sol attempt. Cancellation, policy refusals, unsent drafts and unexpected chat changes stop the chain.
4. Only a text response containing a nonempty task-summary section is accepted; a historical answer or tool request is rejected. This structural check cannot guarantee perfect factual fidelity.
5. Native PreCompact/PostCompact hooks reset tracking for the main context, so the next main turn bootstraps the authoritative compacted native conversation.

Sending the full pre-compaction source can take several UI messages and minutes. Summaries are lossy; continue using fresh file reads to verify current state. A client-configured 500k threshold and selected-account acceptance do not prove a provider-wide 1m deployment limit.

## Cancellation and recovery

Completed native replies with invalid JSON syntax can receive up to five format-only corrections in the original verified chat, sharing the original inference deadline rather than restarting it. Short follow-ups state that the malformed reply was not delivered and none of its proposed tools ran. The bridge keeps model, lane, conversation and epoch, with fresh attempt IDs discarding duplicate/late results. System instructions, tools, history and verified images are not sent again. Only validated corrected output reaches native execution. A visible notice reports the actual count. Source-free metadata records `contextKind: format-correction`, `formatAttempt: 1..5` and transmitted character count.

This applies to syntactic JSON failures in replies that start with a JSON envelope/code fence, or leading commentary followed by one complete suffix that passes the original response/tool-schema checks, with authenticated conversation evidence. A suffix is only eligibility evidence, never executed directly. Invalid arguments, arbitrary prose, policy refusals and unknown delivery do not qualify. Canonical refusals are terminal. Correction stays in the same chat/model and stops at five corrections or the original deadline, reporting the count and cause. Cancellation retains the verified original input checkpoint, including an unsent correction. Existing uncertain records do not acquire evidence retroactively.

The bridge separately tracks browser-delivered input and native-committed history. Cancellation enters a confirmation phase for up to 15 seconds. The authenticated receipt binds job ID, nonce, conversation, lane, page instance and message fingerprints; it is stored before acknowledgement. The page must have no Stop button, an available input and stable evidence across observations. No reply, partial JSON and a just-completed reply are all valid cancellation states. None of their proposed tools is returned for execution.

Explicit new feedback waits for this phase. Verified cancellation continues the original chat and epoch with a tail replacement containing new feedback and actual tool results. Unchanged instructions and tool definitions are omitted. Merged tool-result feedback and trailing system environment messages are supported. Native clients may withdraw a cancelled standalone text prompt before sending replacement feedback; that text tail can be replaced only when every earlier message matches and the checkpoint proves it contained text alone. Tool-result replacement, reminder-only changes and legacy checkpoints without that proof do not qualify. An incomplete first/bootstrap transfer cannot borrow context from a different chat.

If the original chat is unavailable or unverified, recovery uses an isolated full rebuild. When owned-page preparation fails before any job reaches Copilot, the worker reports `submitted:false`, the gateway releases the attempt marker and a subsequent request reuses that preparing tab. This also works after restart or a correlated not-sent cancellation. It is not a lifetime feedback counter. Unknown/partial delivery remains blocked with its actual cause; the attempt marker cannot hide it. The original page and drafts remain intact. A successful rebuild adds a visible synchronization notice. Oversized recovery fails explicitly; ordinary feedback uses deltas and genuine compaction/history rewrites remain full sync boundaries.

If the paired main tab disappears after the native client has started but before its first main request, a completed auxiliary title must not strand that request in the queue. A cancellation-capable worker verifies the original binding even when its last readiness flag is false. Only an explicit conversation-unavailable failure with submitted=false permits one isolated bootstrap recovery. The first committed context keeps epoch 1 consistently in the prompt, response and registry. Transiently hidden panes can recover in place; unknown delivery and provider refusals do not trigger this fallback. Startup before any ready pairing still requires the normal workbook/pairing checks.

Provider refusals are terminal and preserve their original error across retries/restarts; no chat/model fallback is attempted. Late refusals tied to the same page and user-input fingerprint are also terminal. Old uncertain records without trustworthy checkpoints cannot invent evidence: use explicit `context-reset --session <native-session-id>` only after checking actual tool effects. Reset does not undo files or commands and does not resolve a provider refusal.

Install matching gateway/extension builds, reload the extension and refresh the workbook; `capabilities.cancelContinuation` must be `1`. Same chat identity, unchanged epoch and smaller transmitted deltas are observable continuity evidence, not proof of provider-side cache hits.

The launcher lists supported Opus/Sonnet 5.5 IDs plus `copilot-gpt-6.1-sol` and `copilot-gpt-6-sol` in session-only `availableModels`. The short launcher aliases are `opus`, `sonnet`, `gpt61` and `gpt6`. Explicitly changing the main model creates that model's independent bootstrap while retaining other model contexts and their terminal failures. Native history and actual tool results remain authoritative; previous tool side effects are not rolled back. Main-model refusal never triggers an automatic model switch. The native classifier remains responsible for each permission decision. Saved global provider/permission settings are not edited.

An authenticated explicit context reset can include a supported `model` deployment ID; the CLI accepts `--model` aliases. This resets only the matching session/agent/model record and leaves session-wide compaction state and other model leases/refusals intact. Without `model`, the existing session/agent reset behavior is retained. This is not automatic refusal recovery.

## Lifetime registry retention

Conversation handles, native session/agent/model contexts and compaction scopes have no fixed lifetime registration-count limit. New entries and restart loading use the same per-record validation, without the old 100-entry ceiling. Existing records are retained rather than evicted, preserving ready chats, uncertain-delivery checkpoints, terminal refusal reasons and running compactions. The limits on request size, active browser work and native context windows are separate; removing a lifetime record cap does not change those controls or Copilot service quotas.
